The single most useful habit

Run git status after every command. It tells you which of the four columns your work is in, and it suggests the next command to type. A student who reflexively types git status is a student who can get himself unstuck without help.

The guaranteed stumble

Run git add index.html, then git diff — nothing appears. Everyone assumes something broke. It didn't: plain git diff compares column 1 against column 2, and after staging they're identical. The question you meant to ask is git diff --staged, which compares column 2 against column 3. Try both in the console above.

03

Merge vs Rebase

The same starting point, two different endings. Press the buttons and watch what happens to the commits — particularly what happens to their names.

Starting point
Your branch split off from main, and main moved on
Before either. You branched off B and wrote D and E. Meanwhile someone pushed C to main. Your work is now built on an out-of-date starting point — that's the situation both commands solve.
git mergegit rebase
What it doesTies the two lines together with one new merge commit that has two parentsCopies your commits and re-applies them on top of the new main
Your commit shasUnchangedAll new. Same changes, different commits
History saysWhat actually happenedA tidier story that isn't literally true
ShapeBranching, with merge bubblesOne straight line
After it, push isNormalRejected — needs --force-with-lease
Safe on a shared branch?YesNo. Never rebase something others build on
Why the force push, and why it isn't reckless here

Rebase doesn't move your commits — it makes brand new ones with new shas and abandons the originals. GitHub still holds the old ones, so the two histories genuinely disagree and a normal push is correctly refused. Use git push --force-with-lease: it refuses if anyone else pushed to that branch since your last fetch. Plain --force silently destroys their work — treat it as a word you don't type.

Neither one is "better"

Merge is honest; rebase is readable. Teams pick one and stay consistent. The rule that keeps you out of trouble isn't about taste: rebasing your own feature branch is routine and fine; rebasing anything other people have built on top of is how you ruin a Friday.

04

Reading a Conflict

A conflict is not an error and you have not done anything wrong. It's git saying: two people changed the same line, and I'm not willing to guess which one wins. It is the single moment git refuses to be clever.

Click any part of the block to identify it
Where did this conflict come from?

    
Pick a line above. The two modes are not cosmetic — the meaning of
      the HEAD side flips between them, which is exactly how people end up
      deleting their own work by accident.


    

      The trap — verified on this machine, not recalled
      
In a merge, HEAD is your branch. In a
      rebase, HEAD is the other branch — the one you're
      rebasing onto — and your own commit is the one on the bottom.

      
The tell: look at the bottom marker. A
      branch name (>>>>>>> feat/x) means merge. A
      sha plus a commit message (>>>>>>> 36043ba (Set the title))
      means rebase. If you're ever unsure which you're in, git status says so on its first line.

Everything is on fire—git rebase --abort / git merge --abort, or git reflog and reset to a known-good sha

    
  


  

    The fear, and the cure
    
Beginners are frightened of git because they believe they can permanently destroy work.
    Show him git reflog. It lists every position HEAD has
    been in for about 90 days, so a commit — once made — is very hard to actually lose.

    
There is one real exception, and it's worth saying out loud:
    git reset --hard destroys uncommitted changes, and nothing can bring
    those back. Which is the argument for committing early and often. A commit is a save point.
